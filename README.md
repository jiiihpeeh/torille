# torille

A Finnish spell checker, and the harnesses that keep it honest.

## Goal

`torille` answers one question: **is this word correctly spelled, and if not,
what did you mean?** It is a dictionary-driven checker, not a statistical one.
The Kotus sanalista supplies the lemmas, the Kotus paradigm catalogue turns each
lemma into its inflected forms, and anything still unknown goes to compound
analysis.

Everything follows from that shape. The sanalista names 104k lemmas, of which
about 48k carry an inflection class, and a class is a *paradigm*, not a rule: the
catalogue tabulates the eight to fourteen forms a member has and the engine's
job is to work out which of them this particular word has. That is a data
lookup with morphology in the middle, and the two halves have to agree exactly.
A checker that inflects `kissaksi` correctly and `kissaaan` wrongly is worse
than one that inflects nothing, because the wrong form is a *suggestion* — the
user is told to write a word that does not exist.

So the project has a second goal that shapes the first: **every form the engine
offers as a correction has to be checked against an external authority**, in both
directions. Not "does the engine produce the right forms" but "does it produce
*exactly* the right forms" — because both halves of that question are
spell-checker bugs, one of each:

* **Recall.** A form that exists and the engine does not offer it is a word the
  checker will reject. `jokina` is a real word — Voikko reads it as `joki` — and
  the engine produces it only as `guessed`, so it is never suggested and the
  user is told their word is wrong.
* **Precision.** A form that does not exist and the engine offers it is a word
  the checker will tell the user to write. `kevydsoratta` is offered as `plain`
  where the right word is `kevytsoratta`, so it is a "correction" away from
  correct.

The second is the one that is easy to skip and expensive to ship. Almost every
early harness only asked the first.

### Crate layout

The root package is the library and is a workspace root. `tools` and `bindings`
are members, so one `cargo build` covers all three. There are no third-party
dependencies in the library: the Kotus files are embedded with `include_str!`
and compiled into the crate, so a consumer needs no data file at runtime.

The binding's library is named `torille_py`, not `torille`, because the Python
module is also called `torille` and having both in one crate is ambiguous. The
Python name comes from `module-name` in `bindings/pyproject.toml`; the Rust
`fn` is `torille_module` for the same reason — a crate-root `fn torille` would
shadow the `torille` crate in every path expression in the file.

## Optional neural reranker (Slice 0 scaffolding)

The library exposes an optional two-role neural component under `src/rerank/`:

```
                 input word
                     │
      ┌──────────────┴──────────────┐
      │                             │
   deterministic path             morphology
   ─────────────────              hypothesiser
   find_bases_with                     │
   (existing code, unchanged)          ▼
      │                          (lemma, features)
      ▼                               │
   ┌─────────────────┐                 │
   │ Suggestion list │                 │
   │ (rich metadata)   │                 │
   └────────┬────────┘                 │
            │                            │
            ▼                            ▼
       ┌─────────────────────────────────┐
       │           reranker              │
       │   (Reranker trait, no-op today) │
       └────────────┬────────────────────┘
                    │
                    ▼
            final ranked list
```

Slice 0 ships only the scaffolding:

* `Suggestion` and `SuggestionSource` carry every field a reranker might
  want — lemma, edit distance, source variant, morphological readings,
  generation confidence, original rank.
* `Hypothesis` and `MorphologyHypothesizer` model the second role: a
  neural model that proposes `(lemma, features)` pairs when ordinary
  edit distance cannot recover them.
* `realize_hypothesis(h, builder, cat)` turns a `Hypothesis` into a
  `Suggestion` via `FormBuilder::forms_of` — the deterministic inflection
  step is the only thing that produces Finnish surface forms.
* `Pipeline` bundles the reranker, the hypothesiser, and `PipelineConfig`
  knobs. `Pipeline::disabled()` and `NeuralConfig::default()` are both
  off; behaviour is byte-identical to today's `torille::suggest::suggest`.
* `suggest_detailed` is the new rich-returning entry point. `suggest`
  stays a thin wrapper for backward compatibility with the C wrapper,
  Python binding, and WASM module.
* `suggest_with_pipeline` is the entry point slices 1+ use; it consults
  the reranker and hypothesiser when they are enabled, and falls back
  to deterministic behaviour when they are not.

The pipeline must never make the existing engine unusable. A broken or
missing model returns the deterministic ranking; the default config does
not load any model at all.

## Training data generation (Slice 2)

`cargo run -p torille-tools --release --bin train_data` produces the
training corpus that slices 3+ will consume. It streams the
Kotus-inflected SQLite databases in `data/`, applies realistic Finnish
typo corruptions, and writes JSONL files under `data/train/`:

```
data/train/
  train.jsonl                     ~75 % of emitted rows
  dev.jsonl                       ~1 %
  test_unseen_lemma.jsonl         ~5 % (entire lemmas held out)
  test_unseen_inflection.jsonl    ~1 % of (lemma, form) pairs
  test_unseen_corruption.jsonl    ~10 % (reserved corruption family)
```

Each line is one training example:

```json
{
  "misspelled":      "jooksee",
  "surface_form":    "juoksee",
  "lemma":           "juosta",
  "voice": "active", "mood": "indicative", "tense": "present",
  "person": "third", "number": "singular",
  "reading":         "[VOICE=ACT][MOOD=INDV][TENSE=PRESENT][PERS=SG3]",
  "ok":              "both",
  "corruption_type": "substitute_random",
  "edit_distance":   1
}
```

The corruption strategies are: `substitute_random`,
`substitute_adjacent` (keyboard neighbours), `delete_random`,
`insert_random`, `transpose_adjacent` (with end-of-word positional
bias + per-pair weights), `double_consonant_add`,
`double_consonant_drop`, `vowel_swap`. The `double_consonant_drop`
strategy is **reserved** for the `test_unseen_corruption` split so
that family is never seen during training.

The pipeline is deterministic given `--seed N`. Internally it uses
`splitmix64` with a per-row RNG derived from `master_seed XOR
global_row_index`; runs on different machines / different core counts
produce identical JSONL output. Per-row corruption runs on a rayon
thread pool; the JSONL writers stay single-threaded to avoid fsync
contention.

Options worth knowing:

```bash
train_data \
  --output data/train \             # default
  --max-rows 0 \                    # 0 = unlimited (read entire DBs)
  --sample-rate 1.0 \               # fraction of read rows to keep
  --seed 0x5d2b8a3ec47109f6 \       # default
  --nominal-db data/kotus_nomines.sqlite \
  --verb-db data/kotus_verbit.sqlite
```

The `--max-rows` cap is on **DB rows read**, not on emitted examples;
at the default `--sample-rate 1.0` and 2 corruptions per form, the full
corpus (~18 M rows) produces ~36 M examples in roughly an hour on a
typical 8-core box.

The pipeline never ships the SQLite databases in production. The
JSONL output is also a development artefact; only the trained model
weights reach production.

## Neural reranker — Slice 3 architecture + training only

The Slice-3 brief asked us to fix a number of architectural issues
before training. The following six were applied:

1. **Bug fix in the case encoding.** The engine has 16 distinct Finnish
   cases (the usual 15 plus the instructive), but the original
   morphology one-hot had `allative` and `essive` colliding on index
   9. `src/tags.rs::Case::ALL` lists them at distinct indices 9 and
   10, and `tags_dump` writes that to `data/tags_layout.json` as the
   single source of truth.

2. **Single source of truth for the morphology layout.** The
   morphology feature space was previously a hand-maintained Python
   mapping in `model.py`, parallel to the engine's enum. This is the
   failure mode the Slice-3 review flagged. The new `tools/src/bin/tags_dump.rs`
   reads the engine's `PartOfSpeech::ALL`, `Case::ALL`, etc. and emits
   `data/tags_layout.json`; `model.py` loads it at module init. Adding
   a Tags variant in `src/tags.rs` forces a regen of the JSON and a
   retrain.

3. **Edit operations as a feature.** Edit distance alone is weak: both
   `talo → valo` and `talo → talo` are distance 1 but very different.
   `src/suggest/levenshtein.rs` gains `levenshtein_with_ops(a, b) -> (distance,
   Vec<EditOp>)` with a backtrace that distinguishes `Match`,
   `Substitute{from, to}`, `Insert`, `Delete`, and `Transpose{a, b}`.
   `rerank_data.rs` serialises each candidate's edit script as a list
   of `{op, pos, from, to}` records; `model.py` encodes that into a
   16-dim multi-hot (4 op types × 4 position buckets). The trainer
   consumes it alongside `edit_distance`.

4. **Bug fix: explicit `unknown` slot.** A second review pass found
   that the morphology one-hot's "unknown" handling mapped missing
   values to whatever happened to be the last slot of each dim --
   `instructive` for Case, `collective` for Number, `middle` for
   Voice, etc. That's a false morphology signal. `tags_dump` now
   prepends an explicit `unknown` slot at index 0 of every dim, and
   `morphology_one_hot` looks it up rather than using `n - 1`.

5. **Character n-gram features.** Mean pooling alone loses character
   order, so `talo` and `alot` look identical. `model.py` adds a
   64-dim hashed-bigram sum-pool alongside the 96-dim mean pool for
   each of the misspelled, candidate, and lemma fields. The bigram
   is hashed with `(ord(a) * 257 + ord(b)) mod dim`; the `256`-multiplier
   is a small prime > 128 to avoid trivial collisions on the doubled-
   AA / pairs. (The hash now takes `dim` as a parameter so the size
   sweep's non-default bigram widths work.)

7. **Listwise softmax loss with raw-logit scores.** The reranker
   scores candidates *relative to one another*, not each candidate
   independently. The new loss is

   ```text
   For each query q and its candidates [c_1, ..., c_K]:
       logits = model(q, c_k)                 # raw, pre-activation
       loss_q = -log(softmax(logits)[correct_idx_q])
   ```

   averaged over queries. Each query contributes exactly one term,
   regardless of how many candidates it has. The forward pass
   returns raw logits (not sigmoid probabilities), so the listwise
   softmax really is `softmax(logits)`, not
   `softmax(sigmoid(logits))` -- the latter is no longer a
   probability distribution.

8. **Position bucketing from op index, not raw pos.** The Rust
   engine emits a constant `pos: 1` for every op (the alignment
   index isn't on the `EditOp` enum yet). The trainer ignores the
   Rust pos field and buckets the op's *index in the ops list* as
   a fraction of `len(ops)`, so the relative position generalises
   to unseen word lengths. An op at index 0 of 4 ops is "early";
   at index 3 of 4 is "late".

9. **Ablation harness.** `tools/train/eval.py --ablations` reports the
   architectural-review's A/B/C/D matrix on the dev split. Each
   ablation zeroes a feature group at eval time (input masking);
   Slice 4 will run the full re-train.

The morphology layout includes a `HasReadings` flag the rerank_data
binary populates from `Suggestion.readings`, but the full per-reading
Tags are not yet forwarded into the JSONL. Slice 4 will replace the
`HasReadings` boolean with the structured readings
(`POS`, `Case`, `Number`, `Person`, `Tense`, `Mood`, `Voice`) once
the Rust binary carries them through.

The new architecture (default ~113k parameters):

```
misspelled --[char embed 96d, mean-pool]----> v_m_char  (96)
misspelled --[hashed bigrams, sum-pool 64d]-> v_m_bigram (64)
candidate  --[char embed 96d, mean-pool]----> v_c_char  (96)
candidate  --[hashed bigrams, sum-pool 64d]-> v_c_bigram (64)
lemma      --[char embed 96d, mean-pool]----> v_l_char  (96)
lemma      --[hashed bigrams, sum-pool 64d]-> v_l_bigram (64)
morphology --[one-hot 62d, layout from tags_dump.json] -> v_morph (62)
edit_distance (clipped to 4, /4)             --->            v_d    (1)
edit_ops    --[multi-hot 16d, 4 ops × 4 pos] ->             v_ops  (16)
                                                                 |
                              concat ----------------------------+
                                  |
                              Linear(559, 192) + ReLU
                                  |
                              Linear(193, 1)
                                  |
                              logit (scalar, raw)

  char_embed       60 * 96                   =   5,760
  w1               192 * 560                 = 107,520
  b1               192                              =    192
  w2               1 * 193                         =    193
  b2               1                                  =      1
  total                                          ~113,666
```

The forward returns the **raw logit**, not a sigmoid probability.
Listwise softmax is applied by the loss (training) and the
false-positive evaluator, not inside the model.

Training (pure numpy, no PyTorch):

```bash
python3 tools/train/train.py \
    --train data/rerank/train.jsonl \
    --dev   data/rerank/dev.jsonl \
    --epochs 20 \
    --output /tmp/torille_reranker.npz \
    --seed 0
```

A size sweep is built in. `--embed-dim` and `--hidden-dim` override the
defaults, and `python3 tools/train/model.py` prints the suggested
sweep at default:

```text
  embed= 64 hidden= 128  params=  62210
  embed= 64 hidden= 192  params=  91394
  embed= 96 hidden= 192  params= 111746    <- default
  embed= 96 hidden= 320  params= 182402
  embed=128 hidden= 384  params= 256514
  embed=128 hidden= 512  params= 339458
  embed=128 hidden= 768  params= 505346
  embed=192 hidden=1024  params= 871682
```

Evaluating a trained model (engine baseline + reranker delta + ablations):

```bash
python3 tools/train/eval.py \
    --weights /tmp/torille_reranker.npz \
    --data-dir data/rerank \
    --report /tmp/torille_eval_report.md \
    --ablations
```

Regenerating the rerank corpus with the new edit-op features:

```bash
cargo run --release -p torille-tools --bin rerank_data -- \
    --input data/train --output data/rerank \
    --max-rows 300 --candidates-per-row 8
```

`rerank_data.rs` calls `suggest_detailed(misspelled)` per row, finds
the positive candidate, samples negatives closest-first, and now
attaches the Levenshtein edit script via `levenshtein_with_ops`.

The Slice-0 scaffolding is unchanged. The new reranker slots into
`Pipeline::default()` whenever a model is loaded; with no model
present, behaviour is byte-identical to today's `torille::suggest::suggest`.

### Slice 3 results — honest numbers

Training on `data/rerank/{train,dev}.jsonl` (300 + 108 rows from a
`rerank_data` run with `--max-rows 300 --candidates-per-row 8`):

| split | gen_recall | engine_top1 | model_top1 | delta | top3 | top5 | mrr | n_eval | n_miss |
|---|---|---|---|---|---|---|---|---|---|
| dev | 1.00 | 0.778 | 0.352 | -0.426 | 0.750 | 0.880 | 0.567 | 108 | 0 |

`gen_recall = 1.00`: the engine surfaced the correct candidate for
every dev row. The reranker's job is purely **ranking** here, not
recovery. (The unseen_* held-out splits were not generated; the brief
fixed the corpus at 300 rows.)

**Architectural-review ablations (input masking on dev):**

| ablation | engine | model | delta | mrr |
|---|---|---|---|---|
| A (chars + edit_distance) | 0.778 | 0.694 | -0.083 | 0.820 |
| B (A + lemma)              | 0.778 | **0.731** | **-0.046** | **0.839** |
| C (B + morphology)         | 0.778 | 0.648 | -0.130 | 0.779 |
| D (full: + edit-ops + bigrams) | 0.778 | 0.352 | -0.426 | 0.567 |

After the pre-training bug fixes (explicit `unknown` slot,
relative position bucketing, raw-logit scores instead of sigmoid,
`edit_ops` without `match`), the cleanest finding is:

- **Ablation B (chars + edit_distance + lemma)** is the closest to
  the engine baseline at -0.046, with mrr 0.839. This is the
  smallest "useful" reranker: characters + edit distance + lemma
  identity.
- **Adding morphology (C) hurts** in this input-masking setting.
  The morphology block contains too few real features today
  (`HasReadings` boolean only, no per-reading Tags yet) for the
  trained model to use it productively; the un-masked version
  (D) takes the published -0.426 hit.
- **Adding edit-ops + bigrams (full)** hurts a lot. The
  `bigram_dim=64` projection is shallow and the edit-ops are
  noisy without per-position tracking on the Rust side.

This is the honest direction for Slice 4: keep the architecture
modest (≈113k params), but feed it **per-reading Tags** instead of
`HasReadings` (so the morphology block has real signal), richer
edit-op features (`from` / `to` characters via the same char
embedding, position computed from the alignment), and a
`log-frequency` prior. With those, the full-model delta should
approach the B-level -0.046.

### What we learned about `koirissa → korissa`

The review singled out `koirissa → korissa` as the kind of ambiguity a
learned reranker should resolve. The probe `tools/src/bin/probe_koirissa`
runs `suggest_detailed` on a handful of ambiguous inputs and prints
the candidate list. For `koirissa` the engine's candidates start
`koirissa (ed=0), koiraissa, koirassa, koirista, ...` and the entire
top-20 is dominated by forms of `koira` / `koiras` / `kaira` /
`karissa`. **`korissa` is not in the candidate list at all**, even
though the edit distance is 1 (delete the `i` at position 2).

The reason is the engine's `find_bases_with`: it uses prefix-3 /
prefix-2 matching to prune the candidate space, and `kori` (prefix
`kor`) shares no prefix with `koirissa` (prefix `koi`). The
Levenshtein-bound check (`max_distance = 4`) accepts it, but the
prefix pruning rejects it before generation.

This is the **hypothesizer** role in the Slice-0 architecture, not
the reranker role. The reranker's value is in choosing among candidates
the engine actually generates; recovering `korissa` from `koirissa`
requires a separate `MorphologyHypothesizer` that proposes
`(lemma = kori, features = PL + INESSIVE)` and asks the inflector to
realize it. Slice 5 will build that.

This is the kind of honest negative result the Slice-3 brief asked
for. The next decision is data-scale rather than architecture. The brief
asks "if no, inspect whether the problem is candidate generation
rather than ranking"; `gen_recall = 1.00` says generation is fine on
this split, so the bottleneck is the reranker. Re-training on a
10×-larger corpus (or shifting to the morphology-hypothesizer role)
is the natural Slice-4 direction.

Note: these are *input* ablations (zero the feature at eval time).
The trained model still expects the feature, so this is a fast proxy
for the full "trained ablation" Slice 4 will run.

## The data

Both Kotus files are tabulations, and both are committed.

**`data/nykysuomensanalista.csv`** — one lemma per line, tab-separated:
lemma, homonym, part of speech, inflection class, and an optional
`Johdokset` derivative flag. 104746 rows, of which
48258 carry a class value and 26751 are classed nouns — the classes 1–51. The
class column is not always a bare number: `9*B` is class 9 with gradation B (a
consonant gradation, as in `kauppa` against `kala`), `9, 50` means two classes,
and 121 rows have a parenthesised class. The parser in `src/kotus.rs` takes the
leading digits, accepts `*X` gradation letters after them, and drops anything
else. There are 146 distinct class values among the nouns, which is why
`report_by_class.py` reports 146 classes and not 51.

The fifth column, `Johdokset`, holds productive derivation flags on the
base row, e.g. `nostaa` carries `FREQ:67` and `jouduttaa` carries
`REFL:52`. `src/expand/derived.rs` expands them through the class engine;
`tools/add_derivation_flag.py` adds and validates flags, and
`tools/make_derived_test_csv.py` writes the experimental copy.

**`data/kotus-tyypit.txt`** — the paradigm catalogue. Each block is a class
number followed by that class's forms, in a fixed order: the singular
nominative, genitive, partitive and illative, then the same four for the plural,
then the rest. The order is a fact about the file, which is why `kotus.rs` can
read a case and a number off a slot's *position* rather than off a label.

**`data/wiktionary-taivutukset.txt`** — paradigms fetched from fi.wiktionary by
`tools/fetch_wiktionary.py`, one block per model word, 27 pipe-separated fields.
This is a test fixture, not an input: `tests/catalogue.rs` asserts that torille
declines every model word the way Wiktionary tabulates it, with a `GAPS` list of
forms the generator does not reach. Each `GAPS` entry carries a staleness check,
so a class fix turns a gap into a failure that has to be removed rather than
into a silently dead assertion.

## Confidence

Every generated form carries how it was built (`src/tags.rs`):

| | |
|---|---|
| `Plain` | A plain attachment of a catalogue ending to the lemma, no repair at all. These are the forms a correction may be drawn from. |
| `Repaired` | Built by repairing the lemma to fit the ending: gradation applied, a vowel epenthesised, an alternation read off the genitive. Real words often enough that the repair is worth making, but the attachment was not a plain one. |
| `Guessed` | Guessed from a type rule with no catalogue form behind it. Accepted as a word; never suggested. |

The `Plain` line is the one the harness judges, and the distinction is not
cosmetic. A `Repaired` form is often a genuine word (`käessä`), so accepting it
is right; offering it as a *correction* is not, because the repair was a guess
about this word. `noun.rs` judges an oblique twice before it will mark it
`Plain` — the stem reading has to be one this lemma actually has, and the
ending has to be the one that stem licenses — and demotes a case that two
certain readings compete for.

A form also carries a *reading*: a `Tags` value with part of speech, case,
number, tense, person, mood, voice, possessive, clitic and polarity. More than
one reading means the word really is ambiguous, and `Form::union` is the
intersection of what all of them agree on — which is what both the binary and
the binding print.

## Command-line tools

```
cargo build --release -p torille-tools
```

The full binary inventory, the Python harness groups, and the license note are
in [tools/README.md](tools/README.md).

```
inflect LEMMA [CLASS] [POS] [--clitic CLITIC]
```
Inflect a lemma and print every generated form with its confidence and reading.
`CLASS` is a Kotus class expression (`73`, `7*D`, `9*B*A*A`); when omitted the
lemma's own class from the sanalista is used. `POS` is a part of speech, Finnish
or English. `--clitic` attaches `ko`, `kin`, `kaan`, `han` or `pa` to every
form.

```
$ cargo run --release -q -p torille-tools --bin inflect -- talo
talo  class 1  substantiivi

## plain (121)
talo                        plain    noun nominative singular
taloa                       plain    noun partitive singular
taloihin                    plain    noun illative plural
taloiksi                    plain    noun translative plural
taloiksiin                  plain    noun translative plural poss 3
...
```

The three confidences are separate sections, so a run reads as "here is what I
would suggest, here is what I accept, here is what I merely tolerate". Note that
`taloiksiin` is in there: the report in [docs/harness.md](docs/harness.md) lists
it as a defect, so the binary's output is also the bug's evidence.

```
lookup WORD [--case NAME] [--unranked]
```
Build the reverse index over the whole sanalista and answer what a word is a form
of, with the readings the index holds. **Not free, but usable**: it inflects all
104 263 lemmas to build the index — 16 957 065 words — which takes about 27
seconds, after which every word it is asked about is instant. An earlier version
of this file called the tool impractical because it had not finished in ten
minutes; that was wrong, and the number here is measured rather than remembered.

The bases come back **ranked**: a base is scored by how many lemmas the sanalista
gives its commonest class, so a noun comes before a verb comes before the
indeclinable pronoun that happens to be spelled like the form. `--unranked` gives
the sanalista's own order instead, and the tool prints that order when it differs,
so the ranking's working is visible rather than asserted. `--case NAME` restricts
the answer to forms carrying that case, which is what disambiguates a word that is
both a noun form and a verb form; `--case none` asks for the words that have no
case at all.

```
$ lookup vastaan
index: 16957065 words, 16809612 suggestible, 104263 lemmas

vastaan is a form of:
  vasta  [9]
  vastata  [73]
  vastaan  [99]

  (the sanalista's own order is vasta, vastaan, vastata)

readings:
  substantiivi illative singular
  adverbi
  postpositio
  verbi singular present first person indicative active
```

The ranking is `ClassPrior` in the core rather than in this binary, so the Python
binding ranks identically — see [FIX_ME.md](FIX_ME.md). How often the answer is
right is measured, not assumed: `tools/test_reverse_lookup_recall.py` asserts that
99.87% of the reference's 626 201 `(lemma, form)` pairs have the right base
*among* the answers, and that ranking beats the sanalista's own order on the first
base by 0.67 points (97.48% against 96.81%). The 2.3-point gap between those two
is not a defect: 5.75% of the reference's words genuinely have two base forms.

A pronoun's forms are indexed even though the sanalista gives a pronoun no
declension number, because a pronoun has no model *because it is irregular* and
this engine writes that paradigm out by hand. `lookup hänen` answering `hän [101]`
rather than "not in the index" is that rule; the sanalista's withholding of a
number is not the same statement as a word not declining.

```
check WORD [WORD...]
```
Is the word known, and if not, what is it closest to? A word is known when the
index has a plain reading for it; otherwise the phonotactic filter is the only
gate. Same reverse-index cost, same caveat.

```
derive BASE
```
The derivational forms of a base word and its reverse derivations. Cheap: it
reads the sanalista and applies the productive rules, it does not build an
index.

```
$ cargo run --release -q -p torille-tools --bin derive -- talo
derivations of talo:
  talolainen                   [ADJ_LAINEN] Adjective
  talinen                      [ADJ_INEN] Adjective
```

## Hyphenation

Finnish line-break hyphenation lives in `src/hyphenation/`. It combines the
MIT-licensed school pattern set with the morphology engine's compound
structure, then applies Finnish typographic policy (minimum fragments, no
inter-vowel breaks except at a compound boundary or an explicit exception).
It is a separate layer: `check` and `suggest` do not call it.

```
$ cargo run --release -q -p torille-tools --bin hyphenate -- \
    veroprosentti tietokoneohjelmointi autonostaja
ve-ro-pro-sent-ti
tie-to-ko-ne-oh-jel-moin-ti
au-to-nos-ta-ja
```

`--json` returns byte/character offsets, source and ranking penalty. The
public Rust API is `torille::hyphenation::{positions, positions_with, split}`;
the wasm export is `hyphenate`. See [docs/hyphenation.md](docs/hyphenation.md)
for policy, offsets, exceptions and the current limitations.

## The Python binding

`bindings/` builds a PyO3 module called `torille` with one class, `Engine`:

```python
from torille import Engine
e = Engine()                          # loads and parses the Kotus data once

e.inflect("kissa")                    # every form, with named fields
e.inflect("kissa", klass="9", pos="substantiivi")
e.lookup("kauppa")                    # [('9*B', 'substantiivi')]
e.words("substantiivi")              # every lemma of that POS with its class
```

The class argument is `klass` rather than `class` because Python will not take
a reserved word as a keyword argument -- `inflect(w, class="9")` does not reach
this code at all, it is a syntax error while the call is still being parsed.

A `klass` is enough on its own, so a word the sanalista has never seen can still
be inflected: `e.inflect("kokeilusanana", klass="1")` returns the full class-1
paradigm of it, with no possessive suffixes (no sanalista row to say the word is
a noun -- pass `pos="substantiivi"` if it is). Without a `klass`, a word that is
not in the sanalista is the one case `inflect` refuses, because there is nothing
to fall back on.

`inflect` returns a list of objects with `word`, `confidence`, `plain`, and the
reading as separate named fields — `pos`, `case`, `number`, `tense`, `person`,
`mood`, `voice`, `possessive`, `clitic`, `negative`, `tags`. Named fields
rather than the binary's printed tag words, because `poss 1pl` and
`third person` are each two whitespace-separated tokens, and positional parsing
of that is exactly the sort of thing that is silent when it is wrong.

Build it into the current environment with:

```
(cd bindings && env -u CONDA_PREFIX maturin develop --release)
```

The `env -u CONDA_PREFIX` is needed because maturin refuses to run when both
`VIRTUAL_ENV` and `CONDA_PREFIX` are set. `--release` matters: the inflection
itself is 0.22ms optimised against 1.3ms unoptimised, and 71ms against 480ms
for the data load.

`Engine.inflect` releases the GIL around `expand::inflect`, so a thread pool
scales across cores for the morphology. Building the ~200 `PyForm` objects
holds it, so the speedup is 1.9x at two threads and degrades past eight — in
practice masked by the 7.5s Omorfi load that dominates any harness run.

## Tests

`cargo test --release --workspace` runs **637** tests: 602 unit tests in the
`torille` library, 26 integration tests in `tests/catalogue.rs`, 6 in the Python
binding, 2 in the tools, and 1 doc test. Say `--workspace`: plain `cargo test` at
the repository root tests only `torille` and reports a clean 602 while skipping
every other target in the workspace.

The unit tests are per module, and the ones worth knowing about:

| file | what it pins |
|---|---|
| `src/grammar/verb.rs` (35) | the verb classes, including `teroittaisi` for the conditional base |
| `src/grammar/noun.rs` (21) | the noun classes, their stems, their lexical cases; `class_stem` and the fixed-stem classes |
| `src/expand/mod.rs` (29) | the pipeline: build a form, then read it back. Also where the stem regressions live — `the_plural_oblique_is_built_on_the_class_plural_stem`, `a_consonant_final_member_takes_the_same_plural_stem`, `the_plural_oblique_does_not_take_the_singular_i` |
| `src/grammar/irregular.rs` (11) | the members that do not follow their class |
| `src/grammar/stem.rs` (8) | class -> stem, and the gradation grades |
| `src/compound.rs` (8) | unknown words: the split, the head, the tail |
| `src/derivation.rs` (6), `src/wordset.rs` (6) | the productive suffixes, and the whole-lexicon word set |
| `src/tags.rs` (8), `src/spec.rs` (4), `src/case.rs` (3), `src/expand/clitic.rs` (4) | the reading and its fields; the parsed catalogue; the reverse case analysis; the clitics |
| `src/expand/build.rs` (9) | the reverse index: that a form finds its lemma, that a merge keeps each base with its own classes, and that the class prior scores a base by its commonest class |

Tests live in a `mod tests` at the bottom of each file rather than in a
separate tree, so the test for a rule is next to the rule. `src/expand/inflect.rs`
is the exception: it has no tests of its own, because everything it produces is
observable through the pipeline and is tested there.

`tests/catalogue.rs` is the one that catches a regression, because it is
data-driven over both Kotus files rather than a list of words someone thought of:

- `every_tabulated_form_of_every_class_is_generated` — every form in the
  catalogue is produced for every member of that class.
- `every_model_word_is_declined_the_way_wiktionary_tabulates_it` — the fetched
  Wiktionary paradigms, with a `GAPS` list and a staleness check on each entry.
- `every_verb_class_reproduces_its_passive` /
  `every_verb_class_reproduces_its_present_passive` — the passive for all verb
  classes, which is where a stem change shows up first.
- `a_repaired_form_is_not_suggestible`,
  `a_form_the_class_does_not_license_is_never_suggested` — the confidence
  contract above, as tests.
- `the_plural_oblique_does_not_take_the_singular_i` — `naisissa`, not
  `naisiissa`. This one exists because an earlier fix broke it.
- `a_consonant_final_member_takes_the_same_plural_stem` — `aakkoset`. This
  is the one that fails without the `rule_applies` guard fix; the other two
  plural-stem tests pass either way.

Those last two are in `src/expand/mod.rs`.

The third kind of test is the harness, which checks the *library* against
external authorities rather than against itself. See
[docs/harness.md](docs/harness.md). One of those is a test in its own right:

```
python3 tools/test_binding_agrees_with_binary.py
```

The harness reads torille's output as grammatical fields, and the binding
reports those fields directly rather than having them recovered from the
binary's printed words. That is only safe if the two agree, so this pins the
agreement: 21 lemmas, ~5300 forms, the same word, the same confidence and the
same reading through both paths.

## Working with a class report

The per-class report is the tool that turns "something is wrong" into a change.
Its output goes in `reports/`, which is gitignored — it is generated, it is
large, and it is reproducible.

```
python3 tools/report_by_class.py -n 5 -j 8 --split reports/classes
python3 tools/summarize_class_report.py reports/noun-classes.json
```

`report_by_class.py` samples `-n` lemmas from each of the 146 noun classes the
sanalista uses, checks each against the oracle, and writes one object per class.
`summarize_class_report.py` groups the findings by *shape* — same status, same
case, same possessive, and the same pair of endings — so one rule applied wrongly
to a hundred classes reads as one line with a hundred classes on it, and the
before/after columns are the two strings to choose between in the code.

Two things about reading the output that are easy to get wrong:

* **The counts are forms, not cells.** Omorfi answers one cell with two strings
  (`kissakseen/kissaksensa`) and each becomes a row, so a wholly absent case
  counts twice. Read the class count, not the form count, for reach.
* **`confirmed` rows are in the report on purpose.** A list of only defects
  cannot be read as "the rest is fine" — the class may have had nine cells and
  eight are missing, and a list of eight bad ones does not tell you that.

`-n 5` is a sample. The largest classes have thousands of members (class 5 has
3619) and five lemmas is a spot check, not a census; raise `-n` when a class is
about to be changed.

**Rank by rate, not by count.** The classes that top a count ranking (`41*E`,
`49*J`, `41*B`, `41*G`, `41*F`, at 300–500 `illegal` forms each) are simply
large — 391 lemmas carry all 15431 of the `illegal` findings, and they are the
most frequent classes. By ratio the order is different again, and much more
alarming: class `50` at 441 `illegal` against 45 confirmed, `33*C` at 352
against 52, `33*F` at 274 against 84, `33*K` at 464 against 164, `9*D` at 367
against 133. And class 27 has a `käsi` defect that a count ranking would not
have surfaced at all: `käessä` and `käistä` are real Finnish words — Voikko
reads them as forms of *käki*, the magpie — so this one is invisible to any
check that asks only "is the right form offered".

## Gates

Before a change lands:

```
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test --release --workspace
python3 tools/test_binding_agrees_with_binary.py
python3 tools/test_reverse_lookup_recall.py
python3 tools/test_experimental_features.py
```

The first two have one trap each, and both have bitten: `cargo test` at the
repository root tests only `torille` and quietly skips the 26 integration tests and
the tools, so use `--workspace`; and `cargo fmt` on this workspace is **not**
clean, because `src/expand/mod.rs` and `src/expand/build.rs` are hand-formatted
around a couple of calls. Check the files you touched, and do not let the
formatter rewrite those two.

`tools/test_reverse_lookup_recall.py` is the gate for the direction the other
three cannot see. The fingerprint digests the *forward* direction — how many
forms each lemma makes — so an index that attaches a form to the wrong base is
byte-identical to a correct one, and the two tree gates never ask the question at
all. It compares against the Kotus reference over 626 201 `(lemma, form)` pairs
and asserts a 99.8% floor, plus that ranking the bases does not make the *first*
base worse than leaving them in the sanalista's own order. Recall rather than
precision, because the reference does not list a form as wrong: absence is
unconfirmed, not incorrect. See [FIX_ME.md](FIX_ME.md) for the measured numbers
and what the remaining 0.15 points are.

And the harness baselines, which are the numbers a change is not allowed to
make worse:

| harness | baseline |
|---|---|
| `tools/check_nouns_with_omorfi.py` | 740 Voikko-confirmed forms checked, **0 missing** from torille, 0 generated but not offered |
| `tools/check_verbs_with_voikko.py` | 22 192 plain forms, **5 466 unrecognised** — 5 271 of them participle possessives, and not one a row both reference sources agree on; see below |
| `tools/check_word_against_omorfi.py` | the full bidirectional check, per word: every confirmed form offered as plain and no `plain` form outside the confirmed set. Exits 0 for a defect-free word (`talo`, `oma`) and 1 otherwise, so it is a probe rather than a corpus gate — `kissa` is 1 illegal (`kissaaan`, the third-person doubling) plus 10 mistagged. The corpus gate is `report_by_class.py`. |
| `tools/report_by_class.py` | exits 1 if any noun class has a defect. Currently 146 of 146, and the reasons are in [docs/harness.md](docs/harness.md#known-defects). |

`tools/check_nouns_with_voikko.py` is **not** a gate and its exit code should
be ignored: it exits 1 with 171 core-case forms unrecognised, and it did so
identically before the possessive work — all 171 are bare forms, none carries a
possessive, and the per-lemma counts are the same at both commits. They are the
pre-existing fixed-stem and gradation defects, concentrated in `onneton` (58),
`hammas` (50), `lämmin` (29), `käsi` (14) and `vasen` (10), and the same
mechanisms as known defect C. It became non-zero when more forms reached `plain`
and the tool stopped skipping them; it is worth knowing *why* rather than
treating it as a gate that broke.

`check_verbs_with_voikko.py` has the same status and a much larger number, and
knowing *why* matters more here, because the count does not mean what a gate's
count would. Of its 5 466 unrecognised forms, **not one** is a row that Kotus-Verbit
and Omorfi both have: 5 323 are `omorfi`-only and 143 are in neither source, so
the probe is not disagreeing with the reference anywhere. 5 271 of them (96%) are
participle possessives — the negative (`laskematontamme`), the past passive
(`puhututtaan`) and the past active (`tulluttaan`, `purreeksesi`) — and for
5 175 of them (95%) libvoikko returns no analysis at all: it does not have
participle possessives as words. The rest are cells like `laskettaen`, the second
infinitive's passive instructive, which libvoikko reads as the present third person
(`laskettaa`) instead.

The figure was `933 plain forms, 0 unrecognised` until the per-class verb engines
began reaching `plain`, and the denominator is the whole story: those 933 were 49
single-word forms per lemma across the tool's 19 sample verbs, where it now offers
1 168. More cells reached `plain`, which is the point of that work rather than a
regression, and a probe pointed at twenty-four times as much paradigm has not become
less accurate. The number that would measure correctness against the reference is
the per-class audit over `ok='both'`, which is `tools/audit_verbs.py`.

`check_nouns_with_omorfi.py` and `check_verbs_with_voikko.py` check coverage
only, because they predate the harness and are kept as they are. They are cheap
and they are a good smoke test; the strict check is the harness, and it does not
currently pass — the known defects are in
[docs/harness.md](docs/harness.md#known-defects).
